# Идеи под рабочий контекст (черновик, не коммитить)

Написано под конкретный сценарий: Java lead, он же менеджер и постановщик
задач — Jira, Confluence, GitLab, Port (getport.io), Claude CLI. Это не список
задач, а варианты; оценка S/M/L как в [FEATURE_IDEAS.md](FEATURE_IDEAS.md).

## Рамка: чем платим за каждую интеграцию

У приложения есть обещание — «no accounts, no telemetry, ничего не уходит
наружу». Любая интеграция с Jira/GitLab/Port его нарушает, поэтому единственная
честная форма — та, что уже отработана на Google Tasks: **расширение, выключено
по умолчанию, токен свой, в UI прямо сказано, куда уходят данные**.

Есть и второй путь, который вообще не расширяет сетевую поверхность
приложения: **не ходить в API самим, а запускать локальные CLI** (`glab`,
`jira`, `claude`), которые у тебя уже авторизованы. Терминал, парсинг вывода и
запуск процессов в приложении уже есть; приложение при этом не хранит ни одного
токена и не открывает ни одного нового исходящего соединения от себя. Для
части пунктов ниже это заметно дешевле и по коду, и по обещаниям — помечено как
«через CLI».

Общий знаменатель всего списка: приложение сильно там, где **текст и файлы**.
Чем ближе фича к «положи рядом с кодом обычный файл», тем она тут уместнее, чем
попытка стать вторым Jira-клиентом.

## Jira

1. **Ключ задачи как ссылка (S).** `PROJ-123` в тексте, в имени ветки и в
   сообщении коммита → подсветка + hover с summary/статусом/исполнителем,
   клик открывает в браузере. Ложится туда же, где уже живут CodeLens и
   декорации Monaco; ветку git-панель и так знает. Самая дешёвая точка входа —
   и дальше от неё всё остальное.
2. **Ветка и коммит из задачи (S/M).** «Создать ветку из PROJ-123» →
   `feature/PROJ-123-slug` из summary; git-панель подставляет ключ ветки
   префиксом в сообщение коммита (сейчас его руками копируют каждый раз).
   Через CLI: `jira issue view PROJ-123 --raw`.
3. **Задача из выделенного текста (M).** Выделил абзац в заметке → «Создать
   задачу»: summary из первой строки, description из остального, проект и тип
   из настроек. Ровно роль постановщика: заметки со встречи → задачи, не
   переписывая руками. Оффлайн-часть (черновик в файле) работает всегда,
   отправка — по кнопке.
4. **Вкладка «Мои задачи» (M).** По образцу `GoogleTasksTab`: назначенные на
   меня и на моё ревью, фильтр по спринту, перевод статуса, log work. Полезно,
   но это самая большая по коду и самая заменяемая браузером часть списка —
   стоит делать последней, если пункты 1–3 приживутся.

## Confluence

5. **Markdown ↔ страница (M/L).** «Опубликовать эту заметку» (page id и space
   в front matter файла) и «Забрать страницу в Markdown». Круг замыкается:
   документы пишутся в редакторе, в git, и уезжают в Confluence одной кнопкой.
   Дорогое место — storage-формат Confluence; разумно поддержать подмножество
   (заголовки, списки, код, таблицы, картинки из `assets/`) и честно
   предупреждать про остальное.
6. **Шаблоны документов (S).** ADR, протокол встречи, 1:1, постмортем — файлы
   в `~/.aurapad/templates`, «Новый документ из шаблона» с подстановкой даты и
   участников. Даже без Confluence это половина ценности пункта 5.

## GitLab

7. **Пайплайн текущей ветки (S/M).** Статус в git-панели, клик — лог упавшей
   джобы **открывается вкладкой как обычный текст**. Редактор с быстрым поиском
   по большому файлу для этого лучше веб-интерфейса. Через CLI:
   `glab ci status`, `glab ci trace`.
8. **MR на ревью (M).** Список «мои MR / жду моего ревью», diff — уже
   существующим `DiffEditor`, комментарий и approve оттуда же. Для лида это
   ежедневная работа, и именно чтение диффа приложение уже умеет.
9. **Создать MR из ветки (S).** Push + MR с заголовком из последнего коммита и
   ключом задачи из имени ветки. Через CLI: `glab mr create`.

## Port (getport.io)

10. **Каталог сервисов под рукой (M).** Quick open по сущностям Port: сервис →
    вкладка с владельцем, ссылками (репозиторий, дашборд, runbook), результатами
    scorecard. Для лида это «кто владелец этого сервиса и что у него с
    качеством» без ухода в портал.
11. **Scorecard как чек-лист (S/M) — поверх п. 10.** Проваленные проверки
    списком с ссылкой на то, что чинить. Хорошо ложится на роль куратора: видно,
    где команда просела, прямо рядом с кодом.
12. **Self-service action (M).** Запустить действие Port (создать сервис из
    blueprint) из приложения. Полезно редко, но зато ровно в тот момент, когда
    заводишь новый репозиторий.

## Java-специфика

13. **Режим лога (M) — самое недооценённое в списке.** Открыть многомегабайтный
    лог: фильтр по уровню, подсветка ERROR/WARN, сворачивание стек-трейсов,
    переход по `at com.foo.Bar.method(Bar.java:42)` в файл воркспейса, если он
    там есть, навигация по времени. Приложение уже быстро открывает большие
    файлы — это его сильная сторона, а не новая инфраструктура.
14. **Запуск тестов из файла (S/M).** `mvn -Dtest=ClassName#method test` /
    `gradle test --tests ...` в уже существующем терминале, кнопка над классом
    и методом (тот же CodeLens, что у HTTP-блоков). Не «встроенный раннер», а
    «правильная команда одним кликом».
15. **Формат и проверка Java без LSP (S/M).** `google-java-format` по
    `Option+Cmd+L` и `javac -Xlint` в фоне для открытого файла — по образцу
    того, как сейчас сделаны ESLint и Python. Полноценный LSP — прямо в списке
    «чего делать не стоит», а это его дешёвые 20%.
16. **Дамп потоков / GC-лог (S).** Свернуть thread dump по состояниям потоков,
    сгруппировать одинаковые стеки. Узко, но в момент разбора инцидента
    экономит много.

## Менеджерское и кураторское

17. **Заметки о людях (S).** Папка `people/*.md`, quick open по фамилии,
    шаблон 1:1, «открытые пункты» = все незакрытые `- [ ]` из этих файлов
    одним списком. Это то, что обычно живёт в чужом SaaS, а по смыслу —
    локальный текст.
18. **Доска действий по всем заметкам (S/M).** Сбор `- [ ]` и `TODO(имя):` по
    всем воркспейсам в одну панель (обход дерева уже написан для поиска), с
    переходом к строке. Оттуда же — «превратить в задачу Jira» (п. 3).
19. **Недельный отчёт (M).** Черновик из фактов, которые лежат локально:
    `git log --author` по всем репозиториям за неделю + закрытые задачи (если
    подключена Jira) + отмеченные пункты из заметок → `.md`, который дальше
    правишь руками. Для роли «куратор» это регулярная ручная работа, целиком
    состоящая из уже доступных приложению данных.
20. **Диктовка в заметку встречи (S).** Диктовка уже есть; не хватает жеста
    «новая заметка встречи» — файл с датой в имени, шаблон, курсор на месте.
    Одна кнопка вместо «создать файл → назвать → вставить шаблон».

## Claude CLI

21. **«Спросить Claude про это» (S) — лучший из LLM-вариантов.** Выделение (или
    файл) уходит в локальный `claude -p` в терминале приложения. Никакого ключа
    в настройках, никакого нового исходящего соединения от приложения: оно
    запускает бинарник, который у тебя и так авторизован, и показывает вывод.
    Это ровно то, что в `FEATURE_IDEAS.md` §9 записано как «LLM-помощник со
    своим ключом», но без хранения ключа и без нарушения обещания приложением.
22. **Сообщение коммита из diff (S) — поверх п. 21.** Кнопка в git-панели:
    `git diff --staged | claude -p "…"` → черновик в поле сообщения. Показывать
    команду, которую запускаем, и не отправлять ничего без нажатия.
23. **Ревью своей ветки перед MR (S/M).** `claude -p` по диффу ветки с
    промптом-чеклистом команды (файл в репозитории) → замечания списком во
    вкладке. Для лида это «первый проход» перед тем, как звать людей.

## Что бы я делал первым

1. **Ключ Jira как ссылка + ветка/коммит из задачи (п. 1–2).** Дёшево, видно
   каждый день, не требует хранить ничего кроме токена только для чтения.
2. **«Спросить Claude» и сообщение коммита (п. 21–22).** Максимальная отдача на
   строку кода, и единственный способ получить LLM, не ломая обещаний.
3. **Режим лога (п. 13).** Играет на том, в чём приложение и так лучшее в своём
   классе, и не зависит ни от одного внешнего сервиса.
4. **Пайплайн и лог упавшей джобы (п. 7).** Через `glab`, поэтому дёшево;
   закрывает самый частый поход в браузер.
5. **Заметки о людях и доска действий (п. 17–18).** Чистый локальный текст,
   ноль интеграций, прямо в роль «менеджер и куратор».

Осознанно **не** предлагаю: полноценный Jira-клиент, встроенный CI-раннер,
Java LSP и чат-панель с LLM внутри приложения — это либо второй VS Code, либо
второй браузер, и в обоих случаях первым умирает то, за что этот редактор
любят.
